<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer console -> Supabase project config | Human-entered OAuth secrets and redirect URIs; a wrong URI or an exposed secret compromises auth. |
| local filesystem -> git repo | `.env.local` holds real credentials; must never cross into version control. |
| browser bundle -> Supabase keys | Only the anon key may reach the client; the service-role key would bypass all RLS if exposed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `.env.local` committed to git | high | mitigate | Task 2 confirms the END STATE `git check-ignore .env.local` passes (adding a `.env.local`/`.env*.local` rule if the scaffold did not already cover it) before writing real values, and asserts no service-role token in `.env.local`; `.env.example` holds only placeholders. |
| T-01-02 | Elevation of Privilege | Service-role key placed in a NEXT_PUBLIC_ var / client bundle | critical | mitigate | Task 2 asserts (grep) no service-role key in either env file; `.env.example` header documents the anon-key-only rule. No Phase 1 code path uses the service key. |
| T-01-03 | Tampering | OAuth open-redirect / wrong callback URI | high | mitigate | Task 1 registers the exact Supabase `/auth/v1/callback` URI in both provider consoles; Redirect URLs restricted to `http://localhost:3000/**` (same-origin). App-level `next`-param validation is enforced downstream in Plan 03's callback/confirm routes. |
| T-01-04 | Spoofing | Email-confirm template not routing to the app confirm handler (unconfirmed users appear confirmed) | high | mitigate | Task 1 sets the confirm-signup template link to `/auth/confirm?token_hash=...&type=email`; the RLS `is_email_confirmed()` write-gate (Plan 04) is the actual enforcement. |
| T-01-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs occur in this plan (console + env-file work only). Package legitimacy is handled in Plan 02 where installs happen; RESEARCH.md `## Package Legitimacy Audit` documents all packages as false-positive `[SUS]` (framework-tier, canonical repos, no postinstall) — no `[ASSUMED]`/`[SLOP]` package requires a blocking checkpoint. |
</threat_model>
