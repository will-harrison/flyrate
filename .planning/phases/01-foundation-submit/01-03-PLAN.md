<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OAuth provider -> /auth/callback | Provider-supplied `code` + client-supplied `next`; both cross into the app and must be handled safely. |
| email link -> /auth/confirm | Client-supplied `token_hash` + `next`; verifyOtp establishes a session. |
| unconfirmed user -> privileged write | An unconfirmed-but-authenticated session must be blocked at the DB, not just the UI. |
| browser client -> Supabase Auth | signOut / signInWithPassword / signInWithOAuth calls. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | OAuth/email open-redirect via unvalidated `next`/`redirectTo` | high | mitigate | `safeNext()` (Task 1) restricts `next` to same-origin relative paths in BOTH `/auth/callback` and `/auth/confirm`; absolute + `//` paths fall back to `/`. |
| T-03-02 | Spoofing / Repudiation | Unconfirmed-email users performing privileged writes (spam/sockpuppet) | high | mitigate | `is_email_confirmed()` SECURITY DEFINER helper shipped in migration 0002 (Task 2); Plan 04's flies-insert `WITH CHECK` calls it — DB-level gate, not just UI (Pattern 6, AUTH-02). |
| T-03-03 | Information Disclosure | CSRF/session confusion on the OAuth callback | medium | mitigate | Supabase's OAuth uses the PKCE/state handshake handled by GoTrue + `exchangeCodeForSession`; the app only exchanges the code server-side and never trusts client-passed identity. Same-origin redirect restriction (safeNext) prevents session token leakage to a foreign origin. |
| T-03-04 | Elevation of Privilege | `is_email_confirmed()` broad SECURITY DEFINER surface | medium | accept | The helper is read-only (`sql stable`), takes no parameters, and only reads `email_confirmed_at` for the caller's own uid — no write path and no injection surface; documented rationale: minimal, parameterless, single-column read. |
| T-03-05 | Spoofing | Post-confirm user bounced to a sign-in prompt (UX contradicting AUTH-02, users re-enter creds) | low | mitigate | Task 2 redirects post-`verifyOtp` straight to the destination (Pitfall 5). |
| T-03-SC | Tampering | npm/pip/cargo installs | high | accept | No new package installs in this plan (uses Plan 02's dependency set). Legitimacy already handled in Plan 02 per RESEARCH.md `## Package Legitimacy Audit`. |
</threat_model>
